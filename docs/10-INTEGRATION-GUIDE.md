# 10 — Integration Guide

## Current Mode

The RFQ module currently runs standalone.

The final Fluid Controls system will contain other modules/services including authentication/customer management and POT.

## Boundary Rule

RFQ business logic must not depend directly on a temporary home-grown login system.

Conceptual interfaces:

    UserProvider
    CustomerProvider

Development implementations may return mock/reference records.

Future implementations may obtain records from the main application.

## User References

RFQ records may temporarily store/reference identifiers such as:

    sales_person_ref
    assigned_engineer_ref
    changed_by_ref

The RFQ module does not administer those users.

## Customer References

RFQ may contain:

    customer_id_ref
    customer_name_snapshot

Customer master CRUD belongs to the parent application.

A snapshot may be useful so historical RFQ context remains readable.

## POT Boundary

POT is a separate team/module.

RFQ team responsibility:

- expose stable RFQ identifiers
- expose FCL Enquiry Number
- expose agreed RFQ/quotation summary
- document contract
- integrate when parent/POT contract is confirmed

RFQ team does NOT implement:

- purchase order workflow
- PO delivery tracking
- POT database internals

## Integration APIs

Initial conceptual endpoints:

    GET /api/v1/integration/rfqs/{rfq_id}/summary

    GET /api/v1/integration/rfqs/by-enquiry/{fcl_enquiry_no}

Future write/event endpoints must only be added after integration requirements are confirmed.

## FCL Enquiry Number

This is an important cross-module identifier.

Rules:

- unique
- generated through one service
- actual company generation rule pending
- never independently generated by multiple modules

## Integration Owner

Advait is the RFQ-side integration owner.

This means Advait coordinates contracts; it does not mean other developers cannot contribute.
